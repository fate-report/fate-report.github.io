# Fate-Report 디자인 그래프 하네스

`fate-report` 앱(Flutter Web 사주·궁합 리포트)의 화면과 문구를 바꿀 때, 한 사람의 취향에 치우치지 않도록
여러 전문가의 진단을 모으고 충돌을 조정한 뒤 결론을 내는 워크플로우다.

## 0. 고정 전제

- **모바일 전용**: 폭 412px 기준으로만 평가한다. PC 레이아웃은 다루지 않는다.
- **대상 사용자**: 사주를 잘 모르는 2030. 처음 들어온 사람이 10초 안에 무엇을 하는 앱인지 알아야 한다.
- **사용자에게 보고할 때**: 결론만 짧게, 쉬운 말로 쓴다. 전문 용어와 과정 나열은 뺀다.
- **배포**: `main`에 푸시하면 GitHub Actions가 실제 사이트에 자동 배포한다. `main` 푸시와 병합은
  반드시 사용자 확인을 받은 뒤에 한다. 커밋도 사용자가 요청했을 때만 한다.

## 1. 그래프 노드(전문가 5인)

각 전문가는 서로의 결과를 보지 않고 독립적으로 진단한다. 가능하면 서브에이전트로 병렬 실행한다.

1. **`brand-strategist` (브랜드 전략가)**
   - 담당: 앱 이름, 첫 문구, 전체 인상, `web/manifest.json`, `lib/content/copy.dart`의 홈 문구
   - 관점: 이 앱이 누구에게 어떤 느낌으로 기억되는가. 나이 들어 보이거나 사무적이지 않은가.
2. **`visual-designer` (시각 디자이너)**
   - 담당: `lib/theme/app_theme.dart`(색·모서리·그림자·그라데이션), `lib/widgets/common.dart`, 이미지
   - 관점: 강조색을 너무 많이 쓰지 않았는가. 카드가 템플릿처럼 보이지 않는가. 글자가 배경 위에서 읽히는가.
3. **`ux-designer` (화면 흐름 설계자)**
   - 담당: `lib/screens/home_screen.dart`, `input_screen.dart`, `result_screen.dart`의 구조와 순서
   - 관점: 한 화면에 요소가 너무 많지 않은가. 입력 단계가 부담스럽지 않은가. 다음 행동이 분명한가.
4. **`copywriter` (문구 작가)**
   - 담당: `lib/content/copy.dart`, 화면 안의 안내문·버튼 이름, `lib/manseryeok/saju_explainer.dart`의 해설 문구
   - 관점: 내부 용어·어려운 한자어가 노출되지 않는가. "~가 아니라" 같은 해명조가 없는가.
     질문·안내는 다정하게, 결과·신뢰 문구는 단정하게 쓰는가.
5. **`first-time-user` (처음 온 사용자)**
   - 담당: 실제 캡처 화면만 본다. 코드는 보지 않는다.
   - 관점: 첫인상, 지루해지는 지점, 귀찮아지는 지점, 믿음이 가는 지점을 솔직하게 말한다.

## 2. 실행 토폴로지 (3-Stage Graph)

```
[안건 입력 + 현재 화면 캡처]
       │
       ├───► [brand-strategist] ───┐
       ├───► [visual-designer] ────┤
       ├───► [ux-designer] ────────┼──► (Stage 1: 독립 진단)
       ├───► [copywriter] ─────────┤
       └───► [first-time-user] ────┘
                                   │
       ┌───────────────────────────┘
       ▼
[Stage 2: 교차 비평]
  - 전문가 의견이 서로 부딪치는 지점만 골라 토론한다.
  - 전문가 의견과 first-time-user 반응이 부딪치면 사용자 반응을 우선한다.
       │
       ▼
[Stage 3: 의장 결론]
  - 합의한 수정 목록(우선순위 순)
  - 하지 않기로 한 것과 그 이유
  - 사용자가 직접 정해야 하는 것(예: 앱 이름)
```

### Stage 1 진단 형식

전문가마다 아래 세 가지만 낸다. 길게 쓰지 않는다.

- 잘된 점 1~2개
- 문제 3개 이내 (어느 화면의 무엇이, 왜 문제인지)
- 문제마다 구체적인 수정안 1개

### Stage 2에서 자주 부딪치는 지점

- visual-designer ↔ first-time-user: 사진·장식을 덜어낼 것인가, 신뢰감을 위해 둘 것인가
- ux-designer ↔ brand-strategist: 화면을 줄일 것인가, 브랜드 설명을 넣을 것인가
- copywriter ↔ ux-designer: 설명을 늘릴 것인가, 항목을 접어 숨길 것인가

### Stage 3 결론 형식

사용자에게는 표 하나와 3줄 이내 설명만 보여준다.

| 화면 | 바꿀 것 | 이유 |
| --- | --- | --- |

## 3. 수정과 검증

결론이 나면 사용자 승인을 받고 수정한 뒤, 아래를 모두 통과시킨다. 하나라도 실패하면 완료로 보고하지 않는다.

1. `node scripts/harness_verify.js` 전체 통과
2. `flutter analyze` 에러 0건
3. `flutter test` 통과
4. `flutter build web` 성공
5. 수정 전후를 412px 폭으로 캡처해 나란히 비교하고, 콘솔 에러가 없는지 확인한다.

캡처하지 못한 화면이 있으면 어느 화면을 확인하지 못했는지 사용자에게 그대로 알린다.
움직이는 효과(빛 효과, 떠오르는 애니메이션)는 정지 캡처에 보이지 않는다는 점도 알린다.

## 4. 지금까지 합의된 디자인 방향

새 안건을 다룰 때 아래와 어긋나는 제안은 Stage 2에서 반드시 이유를 따진다.

- 홈은 짧게 유지한다. 같은 모양의 카드를 4개 이상 반복하지 않는다.
- 첫 화면 사진은 유지한다(처음 온 사용자가 신뢰를 느끼는 요소).
- 강조색(골드)은 줄이되, 첫 화면의 시작 버튼은 밝고 눈에 띄게 둔다.
- 입력 첫 단계는 꼭 필요한 항목만 보이고, 선택 항목은 접어 둔다.
- 자주 묻는 질문 같은 보조 정보는 접어 둔다.
- 내부 용어와 어려운 한자어는 화면에 내보내지 않는다.
